# Immutable receipt snapshot version 2

New payouts now save a version 2 receipt snapshot atomically with the business record and durable anchor job. Existing receipts remain version 1 and keep their original hashes, records and verification dispatch; no silent backfill or hash rewrite occurs.

## Captured evidence

The deterministic payload uses format ayudachain.receipt, version 2, integer centavos and UTC recording time. It captures the exact payout/household/batch/allocation references, verification-method label and captured file reference; authenticated recording account ID/display name; registry name, DAFAC reference, locality and eligibility status at recording; batch labels/source/purpose/grants; allocation labels/amount; exact stored OCR text; and available receipt bytes' SHA-256, size, source filename and media hint. Encoding is sorted-key JSON, compact separators and UTF-8 without ASCII escaping. It is the documented AyudaChain format, not a claim of a universal canonical JSON standard.

Registry and funding labels may later change without rewriting this captured original. Current payout fields, OCR, captured bytes and media remain reconciled with it during verification and recovery. A snapshot-only alteration remains part of the recalculated hash, so unchanged live values cannot conceal it. A mismatch is declared only after a reliable actual anchor read; unavailable/unanchored outcomes remain distinct. The contract and bytes32 anchor interface are unchanged.

The additive receipt_snapshots table saves the canonical payload and available bytes. SQLite startup installs update/delete refusal triggers; explicit isolated fixture resets reinstall them. There are no snapshot update/delete API routes. A privileged database operator can bypass local protection, so independent chain comparison remains necessary; this is not protection against all privileged storage administration or a complete blockchain audit-history system.

## File and privacy boundaries

Capture uses existing operator-provided files in the configured receipts directory, limited to 2 MiB. This feature adds no arbitrary browser upload/intake or identity-document validation. Local reference/path checks and known legacy/v2 file ownership prevent capturing a source associated with another area. Unassigned files in that operator-controlled folder are treated as synthetic supplied evidence, not verified ownership. Original source files are not modified. Captured bytes are served through the existing protected receipt scopes from the snapshot, even if the source file later changes. Responses include no-sniff and restrictive content-security headers. Media type is a captured hint, not document authenticity validation.

MISSING evidence is explicit and never silently populated later. SHARED_TEMPLATE evidence stays labeled as a template that may describe another fictional household. Scoped Disbursing/Beneficiary views continue to hide its image and OCR, including snapshot OCR; office readers retain inspection access. Scoped snapshot projections can therefore be redacted and are not sufficient for independent reconstruction of every private field. Public receipt indexes and proof responses remain reference/hash-only (with a format version), without snapshot identity or documents.

The private receipt view separates **Captured receipt snapshot (version 2)** from current registry labels and explains available, missing and shared-template bytes. Version 1 explicitly reports that no v2 snapshot was backfilled. Captured registry labels and OCR are saved statements, not proof of real household identity, document authenticity, camera decoding or physical cash delivery. A successful hash check covers this version's captured data only. Recipient acknowledgement remains separate local account evidence, not part of the pre-existing receipt hash.
