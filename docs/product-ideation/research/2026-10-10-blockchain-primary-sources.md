# Blockchain integration: primary-source research

Research date: **2026-10-10**, Asia/Manila. Status: **research and proposed engineering choices, not an implementation specification or deployment approval**. Official documentation is a snapshot as accessed on this date; timings, fee rules, provider features and limits should be rechecked before implementation.

## What the pivot already settles

The pivot is beyond a bare workflow idea. Its [process document](../process.md#consolidated-commitments) already specifies the following logical commitments: fund releases and supporting files; linked reversing/replacement entries; documented amount-input versions; signed barangay batches and council resolutions; explicitly labelled system-fallback snapshots; approved-list versions; handover receipts; and separate outcome events, including timeout, late and amended answers. It also separates business state from anchor state and waits for a confirmed list anchor before publication. These are **Decided ideation**, not built features.

The same process keeps household registration, individual responses and decisions, grievances, sessions, notifications and access logs off-chain. Relevant claim/response/decision versions enter batch/list snapshots. Payouts require a connection; there is explicitly **no offline mode**. The [roles](../roles/) remain application roles, not independent blockchain validators. Version 1 is funds plus a read-only Auditor; the full five-role process is later scope.

Repository evidence: [the Solidity registry](../../../contracts/contracts/AyudaChainRegistry.sol) already has an append-once generic `anchorRecord(recordId, recordHash, recordType)` and public `anchoredRecords` getter. [The existing ethers CLI](../../../contracts/scripts/blockchain_client.js) does not expose either operation. Generic anchoring is therefore reusable for a narrowly scoped local feasibility exercise without changing Solidity. It does **not** independently publish the pivot's explicitly recorded fund/correction amounts and disaster references: the generic record contains a hash and type, while legacy `releaseFund` contains an amount but no source-document hash. Full fidelity needs an explicit compatibility/design decision, potentially a new versioned registry. `allocateFund` represents the old barangay-budget model and should not be reused to simulate the new claims flow.

## Architecture choice and the trust it adds

| Candidate | Evidence | Fit for this pivot | Main limitation / condition to reconsider |
|---|---|---|---|
| Public EVM commitment registry, Polygon Chain/PoS candidate | Polygon supports ordinary JSON-RPC and publicly readable EVM records; official network/finality documentation is linked below | **Proposed first choice** for an externally inspectable commitment history while one Field Office operates the application; reuses Solidity/Hardhat/ethers | The application can still submit false evidence or omit evidence. Public transactions expose timing, addresses, types and linkage. Fees, RPC reliability and key governance are operating obligations |
| Permissioned Hyperledger Fabric consortium | Fabric supports organization-based endorsement policies and private-data collections; the collection's private data goes only to authorized peers while its hash is written to channel peers | **Conditional alternative** when DSWD, LGUs and other willing institutions need independently operated shared workflow infrastructure | Needs named participating organizations, certificate/membership policy, peers/orderers, operational ownership and dispute governance. A one-team network does not independently constrain that same team's history |
| PostgreSQL with signed append-only history and independently retained checkpoints | PostgreSQL provides transactions/privileges. Transparency-log specifications demonstrate signed Merkle history with inclusion and consistency checks without cryptocurrency | A useful baseline and a viable non-blockchain solution if a trusted institution/auditor can retain and compare checkpoints | Database controls alone do not constrain administrators. Signing alone does not prevent an operator presenting different histories; independent observation is required |

Fabric's endorsement is technical validation by configured organization peers. It does not imply a human COA officer must approve a payment. If Fabric is reconsidered, preserve the pivot's read-only Auditor and decide network participation separately from business permissions. [Fabric endorsement policies](https://hyperledger-fabric.readthedocs.io/en/latest/endorsement-policies.html), [Fabric private data](https://hyperledger-fabric.readthedocs.io/en/latest/private-data/private-data.html).

WFP provides a useful counterexample to the assumption that humanitarian blockchain must be public. Its Building Blocks network is privately managed and jointly owned/managed by participating humanitarian organizations, aimed at coordinating assistance across organizations. **Inference for AyudaChain:** its strongest lesson is shared institutional coordination; this is not evidence that one Field Office needs a Fabric consortium today, or that WFP's architecture proves cash-handovers true. [WFP Building Blocks](https://www.wfp.org/building-blocks).

RFC 9162 distinguishes a Merkle inclusion proof from a consistency proof that checks append-only growth, and discusses inconsistent views presented by a misbehaving log. **Inference:** a signed database alternative must distribute checkpoints to independent observers, not merely store its signatures beside data under the same administrator. AyudaChain need not implement the certificate-specific protocol. [RFC 9162, introduction and sections 2.1.4 and 11.3](https://www.rfc-editor.org/rfc/rfc9162.html).

PostgreSQL privileges can restrict UPDATE/DELETE/TRUNCATE by the ordinary application role; RLS can constrain record visibility. Superusers and BYPASSRLS roles bypass RLS, and owners normally do too. **Inference:** these are strong application controls, not external evidence against a database administrator. [PostgreSQL privileges](https://www.postgresql.org/docs/current/ddl-priv.html), [row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

## Current Polygon facts and confirmation policy

Official documentation currently lists **Amoy testnet: chain ID 80002, Sepolia parent, POL gas token**; **Polygon mainnet: chain ID 137, Ethereum parent, POL gas token**. Public RPCs may impose traffic/rate restrictions. Use configured chain ID and contract address rather than infer a network from a URL containing `amoy`. A local node, public testnet and mainnet must be labelled distinctly. [Polygon RPC/network reference](https://docs.polygon.technology/pos/reference/rpc-endpoints).

Polygon's current Heimdall v2 documentation describes milestone-based deterministic finality, typically **2–5 seconds**, separate from later Ethereum checkpoints. It exposes the `finalized` block tag through `eth_getBlockByNumber`. This is a protocol/documentation claim, not an end-to-end application latency guarantee. **Proposed policy:** confirm successful execution in a canonical block covered by the finalized head, then read the expected commitment from the configured registry at finalized state. Submission or a transaction hash alone is insufficient. RPC support and canonical block/receipt handling need integration tests. [Polygon finality](https://docs.polygon.technology/pos/concepts/finality/finality), [milestone mechanism](https://docs.polygon.technology/pos/architecture/heimdall_v2/milestones).

Ethers v6 receipts expose transaction hash, block hash/number, execution status, actual gas used and actual gas price. **Proposed policy:** persist those actual references; reject reverts and mismatched registry contents, and keep submission uncertainty visible until reconciled. A receipt's presence alone is not a record-integrity check. [Ethers v6 provider/receipt API](https://docs.ethers.org/v6/api/providers/#TransactionReceipt).

Local development needs a separately labelled local confirmation policy because it does not represent Polygon milestone finality. Amoy is appropriate for a later explicitly authorized public-testnet trial, not permanent operational evidence. No public-network deployment is authorized by this research.

## Proposed commitment design and privacy boundaries

**Proposal:** private immutable records/files plus minimal public commitments. Each record version should have a fresh opaque ID and versioned envelope containing event type, evidence hashes, relevant decision/list/input versions and predecessor references. A correction appends linked new versions. An outcome is a new event, not an edit to a handover. A source file needs a hash of its exact stored bytes; OCR/parsed values are separate derived evidence. Printed names, stamps and images of signatures do not become authenticated signatories because the bytes are hashed.

For a new payload definition, document encoding, key order, Unicode handling, time format, integer minor-unit PHP amounts, hash algorithm and domain/schema version; publish cross-language test vectors before anchoring. Do not change existing receipt serialization silently. A migration/ADR and maintainer decision are required for changing the current receipt payload or contract surfaces.

Fabric's own documentation warns that predictable hashed data can be guessed by hashing all possible values and recommends secure random salt. **Inference applied to this design:** a hash of only `received_full` / `received_less` / `not_received`, a PIN, ID number or a small amount range is not private. Use a fresh cryptographically random nonce (for example, 32 bytes) within each new private event envelope; retain it privately so an authorized verifier can recompute the commitment. Avoid reusable public household identifiers and never disclose codes or credential hashes to chain. [Fabric private-data security guidance](https://hyperledger-fabric.readthedocs.io/en/latest/private-data-arch.html#protecting-private-data-content).

Private randomness does **not** conceal transaction timing, sender addresses, public record types, linked transaction references, or publicly disclosed fund amounts. A unique receipt linkage can correlate later complaint/outcome traffic. **Proposed review:** evaluate this metadata exposure before a public pilot and retain the settled rule that private outcome answers themselves stay off-chain. Batching is a possible later mitigation, not an already Decided change.

**Merkle option, conditional:** a list root can commit many private entitlement/decision leaves and let a household verify inclusion without receiving everyone else's record. OpenZeppelin's standard tree uses ABI-encoded Keccak256 leaves with double hashing and supports matching Solidity/JavaScript proof verification. Use its documented conventions and keep proof material access-controlled; do not publish a full `tree.dump()` containing private leaves. This would add a dependency and require approval before implementation. [OpenZeppelin merkle-tree source/readme](https://github.com/OpenZeppelin/merkle-tree), [MerkleProof source](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/master/contracts/utils/cryptography/MerkleProof.sol).

**Tradeoff:** one canonical snapshot hash is simpler initially; a Merkle root becomes useful when selective beneficiary inclusion proofs are a requirement. Neither proves that every eligible household was included, that the published version remains current, or that an attestation is true. Latest list/version references and cancellation holds still need server enforcement. Off-chain verifiers can validate a proof against the root read from chain; a new on-chain proof-verification function is not automatically necessary.

**Signatures, conditional:** EIP-712 supports typed message signing and domain separation, but the standard leaves duplicate/replay handling to the application. If future staff cryptographic attestations are needed, bind operation/version, chain/contract domain, nonce and expiry; define account-to-key enrolment, revocation and recovery. A server relay key is not proof that each named officer signed. Beneficiaries need not manage crypto wallets merely to use the payout flow. [EIP-712 specification and replay considerations](https://eips.ethereum.org/EIPS/eip-712).

For a future registry, constrain anchor writes separately from operator administration and retain old anchors on key rotation. OpenZeppelin documents role administration and delayed two-step default-admin transfer; it also warns that access control does not itself constrain a malicious administrator. A small registry should avoid upgrade features that let administrators rewrite old evidence. This is proposed key governance, not a selected new dependency or contract implementation. [OpenZeppelin access control](https://docs.openzeppelin.com/contracts/5.x/access-control).

## Proposed stack and reliable anchoring

| Layer | Recommendation | Basis / operating boundary |
|---|---|---|
| UI | Retain Next.js App Router, React and TypeScript | Already used by `frontend/package.json`; no rewrite needed. Public verify pages must disclose only authorized/private-safe proof contents. [Next.js App Router](https://nextjs.org/docs/app) |
| Business API | Consolidate on Python FastAPI with Pydantic and SQLAlchemy for the implemented pivot | Proposed future backend decision: typed validation/OpenAPI fits multiple roles and versioned payloads. Current root scripts still run `backend/server.py`; the drifted FastAPI app is not ready merely because it exists. Confirm target before implementation. [FastAPI features](https://fastapi.tiangolo.com/features/) |
| Database | PostgreSQL for role-enforced multi-user operations, versions, audit and durable anchor work | Store business change, audit event and anchor-work intent atomically. Local SQLite may remain for a limited feasibility demo. A schema/provider migration requires approval. [PostgreSQL transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html) |
| Chain submission/read | Retain Node.js with existing ethers v6; move reliable submission/reconciliation into a small worker | Reuses current Solidity client. One initial submitter per signing account simplifies nonce concurrency; read verification does not need its private key. Python web3 is an alternative only if consolidating runtimes outweighs preserving tested ethers code |
| Evidence | Private object storage, immutable file-version references and authorized retrieval | Supabase private Storage is a viable managed candidate; S3 with versioning/Object Lock is a stronger retention option when the retention requirements justify it. A signed URL is a limited-time bearer capability; the API still decides who may receive it |
| Authentication | Real staff authentication plus API authorization before five-role rollout | Supabase Auth is a candidate if managed Postgres/Storage is selected; use named staff accounts and server-side role, barangay, session and conflict checks. Identity/authentication and payout codes remain different capabilities |
| Notifications | Independent notice-delivery adapter and delivery history | Phone OTP provider, Philippine deliverability/cost/registration and recovery remain unresolved. Payout notices are not recipient authentication and never contain the handover code |

Supabase private buckets require authorized download or limited-time signed URLs; public buckets permit anyone with the URL to retrieve files. Its service keys bypass Storage RLS entirely, so a FastAPI endpoint using one must authorize every record/file access itself. [Supabase storage access model](https://supabase.com/docs/guides/storage/buckets/fundamentals), [Storage access control](https://supabase.com/docs/guides/storage/security/access-control).

AWS S3 Object Lock requires versioning and protects particular object versions; adding a new version does not mean that new version inherits the old version's protection. Governance mode permits privileged bypass, while compliance mode prevents deleting/overwriting a protected version during its retention period. **Proposal:** select retention deliberately after institutional requirements are established, and store the exact evidence version ID. Versioning alone should not be described as enforced immutable retention. [AWS S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html).

Supabase phone OTP requires a separately configured SMS provider and has rate/cost considerations. Its existence does not establish free SMS, Philippine carrier feasibility, household sharing, PIN recovery, or authenticated basic-phone outcome replies. Keep phone authentication **Proposed** until those assumptions are tested. [Supabase phone sign-in](https://supabase.com/docs/guides/auth/phone-login).

**Proposed reliability pattern:** use a durable transactional outbox. AWS's primary guidance explains the database/message dual-write problem, saving the event intent in the same database transaction and idempotent handling of duplicates. Applied here: commit the immutable business version, `audit_events` and anchor job together; a restartable worker later submits/reconciles the same commitment. This is eventual anchoring, not a transaction spanning PostgreSQL and blockchain. [AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).

FastAPI's background-task facility runs work after a response; it is not presented as a durable anchor queue. **Inference:** do not make it the sole record of required anchoring work. PostgreSQL's `SKIP LOCKED` supports multiple consumers of queue-like tables, so an initial PostgreSQL-backed worker does not inherently require Redis/Celery. Add a broker only after measured throughput/operational needs justify it. [FastAPI background tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/), [PostgreSQL SELECT locking](https://www.postgresql.org/docs/current/sql-select.html).

A worker must reconcile an unknown submission before retrying: inspect saved transaction references and the registry's version ID/hash; a nonce/replacement strategy must not create a second business record. Outcome anchoring never authorizes another handover. Browser acknowledgement loss requires reading the same transaction after reconnecting. The durable queue is a **server-side chain-retry mechanism**, not permission for offline cash payout.

## Cost sensitivity, not a price quote

Polygon Gas Station's current documentation derives recommendations from recent `eth_feeHistory`, and states a mainnet minimum priority fee of **25 gwei**. Effective gas price also depends on base fee and actual inclusion conditions. Budget from measured deployed-contract gas and recorded receipts, rather than a generic advertised per-transaction price. [Polygon gas guidance](https://docs.polygon.technology/tools/gas/polygon-gas-station).

Calculation: `fee in POL = gas used × effective gas price in gwei × 10^-9`.

The following is an **illustrative sensitivity calculation**, assuming 100,000 gas per transaction. That gas figure has not been measured for a pivot registry; 25 gwei is a boundary illustration, not a guarantee or live effective fee.

| Effective price assumed | Fee per anchor | 20,000 anchor transactions |
|---|---:|---:|
| 25 gwei | 0.0025 POL | 50 POL |
| 50 gwei | 0.005 POL | 100 POL |
| 200 gwei | 0.0200 POL | 400 POL |

For example, 10,000 handovers plus one closing outcome each produce 20,000 transactions **if each event is anchored individually**. This excludes fund/files, list/input/batch snapshots, timeout then late answers, amended outcomes, reverts, contract deployment, replacement submissions, RPC subscriptions, storage/egress, compute and SMS. FIFO work ordering and batching can alter both gas and latency; benchmark them before selecting them. No fiat cost is claimed without a dated POL exchange rate and a defined deployment.

## Evidence limits and decisions still required

- **Meaning of verification:** a finalized matching commitment establishes that presented content matches a recorded commitment. It does not establish authentic source documents, affectedness, eligibility, full cash receipt, absence of omitted events or absence of corrupt collusion. Say “record integrity matches” separately from human approval and recipient confirmation.
- **Independent use:** an Auditor should be able to check a configured network/registry through an independent RPC with authorized evidence and published hash rules. An application-owned green badge alone preserves dependence on the application. This is an engineering proposal; packaging formal exports remains Later in the pivot.
- **Unanchored history:** the settled inventory does not anchor every S11 event or S12 access log. Do not claim that all audit history is externally immutable. Signed checkpoints or additional event anchoring are possible scope changes, requiring a maintainer decision.
- **Source authenticity:** hashes and EIP-712 do not authenticate photographed handwritten signatures. Define real digital-signature validation separately when supported documents and issuing organizations permit it.
- **Privacy governance:** NPC's publication of RA 10173 establishes purpose/proportionality, limited necessary retention, security and rules for sensitive data. It does not approve this design, automatically classify commitments as anonymous, or authorize putting beneficiary details on a public ledger. Determine actual processing authority, disclosure and retention with the institution before a real pilot. [NPC: Data Privacy Act, sections 3, 11–13, 16 and 20](https://privacy.gov.ph/data-privacy-act-/).
- **Institutional process:** detailed ECT rules already researched in [the pivot process](../process.md#research-used-in-this-decision) remain the reference for activation, FACED, signatures and payout boundaries. DSWD web pages timed out and the COA GAM HTML returned HTTP 403 in this research session; no new legal/accounting claim is based on those unread pages. Blockchain records do not stand in for funds certification, cash advances, banking or liquidation, which the pivot keeps outside active scope/Later.
- **Next decisions:** backend target/consolidation; public-chain versus consortium trust model; generic proof prototype versus full typed registry; explicitly public fund amount/disaster/linkage fields; canonical payload/version/migration; nonce/privacy scheme; finality/RPC contract; relay/admin key governance; evidence retention/backup; real authentication and SMS feasibility. None was resolved by installing packages, changing schemas/contracts, or deploying during this research.
