# Household to payout handoff

Bounded frontend follow-up to [PR #25](https://github.com/andreirtc/ayudachain/pull/25). The existing registry link discarded the inspected household, requiring Disbursing to find it again and showing readers unrelated permitted payouts. The handoff now carries `beneficiary_id` to `/distributions` and keeps the exact household through payout entry, recorded payouts and receipt links.

Disbursing sees the linked household selected with its current batch, approval, allocation and grant constraints. Selection is locked while the link is active; **Choose another household** returns to an empty entry. Other permitted roles see only the linked household's recorded payouts, with **View all permitted payouts** to remove the filter. Search narrows these records without broadening the household filter. Direct entry without a household link still starts with no selection. **Record another payout** leaves the household filter and opens an empty form.

The target must occur in the authenticated API's permitted household list. Unknown, empty and out-of-scope links show **Household unavailable**, hide payout entry and records, and never substitute another household. Query values are encoded and matched by exact ID rather than names. Changing the linked ID remounts the task, clearing the previous household's form, errors and saved result. Refresh failures block saving and hide older records; a successful retry retains the linked household and entered amount.

Readers can follow the registry link for pending, rejected and retained households as well as approved households. Barangay retains its existing registry-only access. Historical records are loaded through the existing scoped API so retained duplicates keep their original payout labels and receipts. They are excluded from ordinary new-payout choices and explicitly blocked from receiving a new payout when linked. Existing server eligibility, alias history, budget, role and idempotency rules remain authoritative.

No API, receipt protocol, account provisioning or chain change is included. Manrope headings, Source Sans 3 body text and the existing branding remain. Receipt checks still establish only the integrity of covered fields, not physical cash delivery.

## Validation on 2026-10-13

All 64 isolated real Edge cases passed at desktop 1440×900 and phone 390×844. Eight new cases cover exact-ID records and receipt links, reload/refresh, empty/missing/out-of-scope references, Beneficiary scope, same-name households, query encoding, pending approval, retained duplicates, centavo amounts, failed-load retries and repeat-payout blocking. Those eight passed again against the final build after making the ordinary journey fixture select an active household rather than assume the newest payout is active. The existing Barangay registration → DSWD review → Disbursing payout → exact receipt journey now uses the registry handoff and passed at both sizes. Desktop and phone screenshots were inspected. Ten existing frontend Node checks, 19 authenticated API permission regressions, independent TypeScript, production build and diff checks passed.

The ordinary browser fixture uses synthetic records in a system-temp database and explicitly unavailable chain verification. These checks do not establish new mining results or human comprehension. Actual-chain evidence from the preceding task remains documented in [UI_VERIFICATION.md](UI_VERIFICATION.md).

The frontend build supports `AYUDACHAIN_BUILD_DIR` for isolated output. This task used `.next-handoff-qa` so the original `.next` build was preserved. On PowerShell, set `$env:AYUDACHAIN_BUILD_DIR='.next-handoff-qa'`, build from `frontend` with `node node_modules/next/dist/bin/next build`, then run `node node_modules/@playwright/test/cli.js test` in the same environment. The existing fixture refuses occupied ports 8101/3101 and stops its owned services afterward. Restore Next-generated `next-env.d.ts`/`tsconfig.json` changes after an isolated build; they are not product changes. The persistent preview remains stopped, and the original database, frontend and chain are preserved.
