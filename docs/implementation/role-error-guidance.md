# Role-specific workflow error guidance

Implemented locally on 2026-10-13 against the MVP baseline `56102c4`. **Publication status: implementation and regression tests committed in `1644f5996de6cc7c55f7c1ea2934fc7a661be648`.** The original implementation results below are retained separately from the fresh publication checks. Runtime logs and generated build outputs referenced below remain local evidence; the later publication includes source snapshots and review assets, not Git-ignored runtime data.

The claim-submission API correctly refused `intake_closed_or_not_covered`, but the UI displayed that internal code and suggested a refresh instead of explaining the missing human intake step. MVP error presentation now explains the obstacle, the responsible role and the permitted next action. The catalogue covers all 175 literal `DomainError`/`RecordedRefusal` codes currently declared in `backend/app`, additional CSV row diagnostics and safe transport fallbacks.

| Selected role | Example | Guidance |
|---|---|---|
| Beneficiary | Intake closed or household outside coverage | Ask Barangay/DSWD to check the selected disaster, intake status and coverage. |
| Barangay Officer | Independent endorser required | Ask another independent officer; do not endorse an own or assisted household. |
| DSWD Officer | Intake, inputs, publication, linkage or assignment missing | Use the relevant Households & intake, Amounts & approved lists or Payout sessions step, with the required evidence and human decision. |
| Disbursing Officer | Handover already recorded or acknowledgement lost | Inspect the current transaction/receipt; never repeat physical cash. |
| Auditor | Inspection logging unavailable | Ask the evaluation operator to restore logging before inspecting evidence. |

`frontend/lib/workflow-errors.ts` holds complete English/Filipino messages. The existing language provider supplies role/language context to the screens and hooks. `WorkflowError` retains the original API code/status for diagnostics; API payloads are unchanged. Client-only failures use status 0 rather than inventing an HTTP response. Original-file error responses and partial CSV outcomes use the same presentation. Unknown API errors and non-JSON gateway replies do not expose raw codes/traces. Invalid UTF-8 uploads tell users how to save a valid CSV instead of showing a browser decoder exception. Other local form validation text remains separate.

Recovery does not reopen closed intake, change recorded coverage, approve duplicates, replace a lost deployment, make a paid entitlement payable again or grant permissions. It explains existing rules. Missing records and unavailable private lookup remain nondisclosing. Lost write responses are uncertain; read saved state before retrying. Read-only POST requests for integrity checks, CSV previews, task searches and session lookup use read recovery rather than suggesting a business action may have saved. `AbortError` is preserved so cancelled former-account requests remain silent. Original bytes, hash payloads, contracts, database schema, audits and backend command rules are unchanged.

Filipino messages follow the existing guidance preference; native-speaker review remains Pending. This is workflow guidance for claimed, unverified actors, not authentication or real-household readiness.
